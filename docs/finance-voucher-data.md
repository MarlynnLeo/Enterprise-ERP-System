# 凭证数据来源与美元记账契约

## 数据来源

| 凭证数据 | 手工录入来源 | 业务生成来源 |
| --- | --- | --- |
| 科目及辅助核算要求 | `gl_accounts` 有效科目及其辅助核算标记 | 会计配置中对应业务的科目 |
| 客户、供应商 | 凭证专用选项接口的有效主数据 | 原销售/采购单及应收/应付发票的往来单位 |
| 部门、成本中心 | 分别选择 `departments.id`、`cost_centers.id` | 明确的业务维度；成本中心关联部门可回带，不能把部门 ID 当成本中心 ID |
| 个人 | `users.id`，保存 `employee_source=user` | 工资来源为 `hr_employees.id`，保存 `employee_source=hr`；来源未知的旧 ID 不猜姓名 |
| 项目 | 明确填写项目名称 | 业务来源中已有的项目名称；不以无关项目表猜测 ID |
| 数量、单位、单价 | 可选明细字段，未填保持空值 | 可明确对应的单一物料来源；不同物料或单价合并时不造一个汇总单价 |
| 发票号、结算方式 | 明确填写的票据元数据 | 原应收/应付发票及收付款记录 |
| 附单据数 | 独立 `attachment_count` | 只有来源明确时保存，不再占用业务票据号 |
| 制单人、审核人 | 当前认证用户及实际过账用户 | 凭证记录关联 `users` 姓名，列表与独立明细共用映射 |

`GET /api/finance/entries/options` 统一返回录入需要的有效引用数据。它只返回用于选择的 ID、编码、名称与核算标记，不暴露用户口令、薪资或联系资料。前端不再通过其他模块的默认分页列表拼装选项；请求失败可重试，重新打开会刷新，迟到的旧请求不能覆盖新结果。

## 金额契约

- 本位币为人民币。借方、贷方、过账余额及财务报表中的金额均为 CNY。
- CNY 汇率固定为 1。USD 必须明确填写原币金额和汇率，汇率含义为 **1 USD = x CNY**，最多 8 位小数。
- 手工 USD 分录必须满足 `人民币金额 = round(美元金额 × 汇率, 2)`，并以人民币验证借贷平衡。前端和后端都采用十进制规则，不能用缺省汇率或由本位金额反推历史外币金额。
- 科目明确配置为 USD 时，普通手工录入必须使用 USD 并填写原币金额与实际汇率；CNY 通用科目仍可记录合规的 USD 分录。此规则不靠科目名称猜测，不覆盖受控历史冲销或内部自动业务，也不表示支持汇兑重估。
- 发票分拆净额、税额产生的最多 0.01 元舍入差，保存为明确的 `base_rounding_adjustment`。只有内部业务生成和受控冲销可使用，手工 HTTP 请求不能借此绕过换算校验。
- 人民币自动合并要求往来单位及对应行的辅助维度一致。美元来源逐单生成，保留每张原单的核销依据，暂不支持把多张美元来源合成一张凭证。
- 过账时再次验证原币换算、借贷平衡、科目及引用主数据状态，避免草稿保存后资料变化导致错误入账。

## 发票与收付款闭环

- 应收、应付发票新增及草稿编辑明确保存币种和汇率。切换 USD 时必须填写汇率；同币种编辑可保留已保存的汇率。确认后禁止修改币种、汇率和财务明细。
- 发票确认生成的应收／应付控制行以 `round(发票原币总额 × 确认汇率, 2)` 为准，不在控制行上调整尾差。净额、税额的拆分尾差分别留证。
- 美元收付款选择同为 USD 的银行账户，并使用发票确认汇率。收付款单、银行流水及发票已收付／余额保存 USD 原币；总账记录 CNY 本位金额。
- 每笔核销保存 `base_settlement_amount`。部分核销本位金额等于“累计原币已核销金额折算值 − 此前有效核销本位金额”；最后一笔取原控制行剩余本位金额，确保原币和本位币同时结清。已作废的收付款不参与累计。
- 收付款表头保存 `currency_code`、`exchange_rate`、`base_amount`；币种与发票不符、银行币种不符、不同确认汇率、缺少原始已过账控制行或历史本位核销证据时拒绝提交。
- 美元暂不支持现金、折扣、退款、跨币种结算及按新汇率结算。前端提示支持范围，后端校验同样生效。应付审批金额按 CNY 本位金额判断。
- 列表和详情明确标记 USD／CNY。现有仅支持人民币的打印模板不用于美元单据，以免输出错误币种。
- 凭证打印在所选模板后追加完整本位/原币、汇率、辅助核算及真实过账信息。应收/应付原单自身的打印仍遵守其币种支持范围。

收付款 HTTP 创建接口支持 `Idempotency-Key`：同一用户、同一内容的重复请求返回原记录，修改内容或用户后复用编号返回409；失败事务不留请求证据，作废后重试返回原作废记录。前端在发送前按用户及收/付款类型存入 sessionStorage，未知结果保留原内容，成功或明确400失败清理。迁移 `20261017000500_add_settlement_request_evidence.js` 保存请求编号、摘要及唯一约束。恢复限当前标签页会话，不跨设备。

迁移 `20261017000300_add_settlement_currency_evidence.js` 添加收付款本位核销证据；`20261017000400_preserve_invoice_exchange_rate_precision.js` 将发票汇率扩为 8 位小数，并保留历史 NULL。

## 客户应收与供应商应付摘要

`/api/finance/ar/customer-receivables`、`/api/finance/ap/supplier-payables` 及其 `/:id` 详情接口均按原币返回，明确标记 `amountBasis: 'original'`。每个往来单位提供 `currencyTotals`，逐币种列出 `currencyCode`、`invoiceCount`、`totalAmount`、`paidAmount` 与 `balance`，不同币种不相加。

- 单币种保持原顶层金额字段并增加 `currencyCode`；仅人民币的数据与旧接口金额兼容。
- 混币时 `hasMixedCurrencies: true`，顶层 `currencyCode`、`totalAmount`、`paidAmount`、`balance` 为 `null`，调用方必须展示 `currencyTotals`；顶层 `invoiceCount` 仍可合计。
- 无有效发票的详情返回 CNY 零金额、空 `currencyTotals`；摘要列表不包含没有正余额的往来单位。已有正余额的混币单位保留其他币种的零余额或负余额组，不相互抵销。
- 详情的 `invoices` 金额也是原币，并带 `currencyCode`、`exchangeRate`、`amountBasis`。历史 USD 缺失汇率仍为 `null`，不推算汇率或本位余额。明细排除草稿、取消及已付清记录。
- 列表在币种内按余额降序排列；混币行没有跨币种金额排序依据，置于单币种行之后。

## 历史记录修复

迁移 `20261017000200_complete_gl_voucher_fields.js` 添加可空辅助字段并将汇率扩展为 8 位小数，不伪造历史数据。

`backend/scripts/repair-gl-voucher-metadata.js` 默认只读分析。它只从已验证的单据链接、唯一的单据号码及一致日期、明确原单明细恢复空辅助字段，保留已有值，包括明确的零值。对多个来源、来源冲突或缺少历史单位快照，报告原因并跳过。

补全范围不包含借贷金额、汇率、原币金额、科目、凭证状态或审批记录。应用时要求明确数据库名，事务内逐行核对空值条件；任何并发冲突都回滚。报告保留每个补值的原始来源，可重复执行验证没有剩余补值。

```powershell
node backend/scripts/repair-gl-voucher-metadata.js --report=output/voucher-metadata-dry-run.json
# 在审核上述实际差异后，明确数据库与凭证范围：
node backend/scripts/repair-gl-voucher-metadata.js --database=<数据库名> --entry-ids=<凭证ID> --apply --report=output/voucher-metadata-applied.json
```
